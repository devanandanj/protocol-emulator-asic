## How it works

PEmu (Protocol Emulator) is a small programmable pin-bit-banging core in
the tradition of the RP2040's PIO state machines and TI Sitara's PRU.
Instead of shipping fixed UART / SPI / I²C peripherals in silicon, the
chip is one datapath plus a 256-word SRAM program memory: the *firmware* picks
the protocol at boot. Reloading a different program turns the same
silicon into a UART, an SPI master, or an I²C master.

The core is a single-issue in-order machine with a 15-opcode ISA
(`docs/isa.md`), a 12-bit program counter, eight 8-bit general-purpose
registers, and two 16-deep 8-bit FIFOs on the host seam (one for host →
core, one for core → host). Every instruction is 16 bits and executes
in one cycle unless it explicitly waits (`DELAY`, `WAIT`, and a blocking
`PULL` when the TX FIFO is empty). Pin-level opcodes drive an 8-bit
`pin_out` / `pin_oe` bus wired to the `uio[7:0]` bidirectional pads.

At boot, the core is halted. The host writes the program into memory
over a small SPI port on `ui[0..2]` / `uo[0]`, then sets the run bit,
and the program starts from address 0. The same port feeds the TX FIFO,
drains the RX FIFO, and reads the IRQ lines while the program runs.

Four example protocols ship in `programs/`:
`uart_tx.pemu`, `uart_rx.pemu` (both 8N1 @ 115200 baud),
`spi.pemu` (mode 0 master, MSB-first, ~1 MHz on a 50 MHz core), and
`i2c_write.pemu` (single-byte master write with ACK sampling). Each one
is verified against a cycle-accurate C++ model: the cocotb testbench
walks the RTL and the model side-by-side and asserts `(pc, regs,
pin_out, pin_oe)` match on every clock edge.

## How to test

After the design is fabricated and mounted on a Tiny Tapeout dev board:

1. Power the board and select this project via the TT commander.
2. Pulse `rst_n` low. The core is now halted.
3. Connect an SPI master (mode 0, SCK at most `clk/8`) to `ui[0]` (SCK),
   `ui[1]` (MOSI), `ui[2]` (CS_N, idle high) and `uo[0]` (MISO). Send one
   frame: `0x02`, `0x00`, then each 16-bit program word low byte first.
4. Optionally queue bytes with a `0x03` frame, then send `0x01 0x01` to
   start the core. `0x01 0x00` stops it. The full command list is in
   `docs/architecture.md`.
5. Program behaviour: `uart_tx.pemu` transmits any byte pushed into the
   TX FIFO (a `0x03` frame) as an 8N1 UART frame on
   `uio[0]`; `spi.pemu` clocks SCK on `uio[0]`, drives MOSI on `uio[1]`,
   and samples MISO on `uio[2]`; `i2c_write.pemu` drives SDA on `uio[3]`
   and SCL on `uio[4]` open-drain. Details in each `.pemu` file's
   header.

For pre-silicon testing, the repository ships a cocotb harness. From the
project root, inside the dev-container:

```
cd test
make
```

runs the ISA walk (`test_step3`) and the four-protocol golden-trace
comparison (`test_protocols`). The trace files live in `test/traces/`
and are regenerated by `build/pemu_sim` at import time.

## External hardware

None strictly required. A 3.3 V logic analyser or a matching USB-serial
adaptor on `uio[0]` (for UART) or `uio[0..2]` (for SPI) is useful to
watch the protocol come out live. For I²C, a slave device (or a pair of
external pull-ups on `uio[3]` and `uio[4]`) is needed because the SDA/SCL
lines are open-drain — the core only pulls them low.
